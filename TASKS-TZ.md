## Логика предсказания (прогноз): как сейчас и как лучше

### Как сейчас

| Файл | Роль |
|------|------|
| `frontend/src/utils/forecast.js` | Числовой **уровень** 1…3 → строка «низкая / средняя / высокая»; **`getLimitCap`**. Цепочка: `baseLevel(доход, возраст)` → `adjustForPurpose(цель)` → `probability` + `limitCap`. |
| `frontend/src/utils/forecastCopy.js` | **Текст** объяснения по `probability`, `answers`, `limitCap` (без дублирования математики). |

Это соответствует ТЗ: «логика в коде, без реального API» и псевдокоду с корректировкой по цели и лимиту по возрасту/доходу.

### Что улучшить в первую очередь (без ML)

1. **Разделить «скор» и «бакет»**  
   Ввести `score` (например 0–100) из взвешенных факторов (доход, возраст, цель), затем порогами маппить в низкая/средняя/высокая. Так проще подкручивать веса и не ловить странные углы при нескольких `±1` подряд.

2. **Таблица правил или конфиг**  
   Вместо цепочки `if`: массив правил `{ when: (a) => …, bump: +1 }` или YAML/JSON в коде — проще ревьюить и менять без переписывания веток.

3. **«Почему так» для пользователя**  
   Возвращать из `getForecast` массив `reasons: string[]` (например «официальный доход», «цель — повседневные траты») и выводить списком под прогнозом — повышает доверие к «честному» прогнозу.

4. **Согласовать текст и правила**  
   Для каждой комбинации `(probability, income, age)` иметь явную строку в объекте или i18n-ключе, чтобы не было рассинхрона между `forecastCopy` и `forecast.js`.

5. **Дисклеймер**  
   Одна строка мелким текстом: «Оценка для прототипа, не офер банка» — снижает юридический и ожидательный риск.

### Что не нужно для этого кейса (по ТЗ и срокам)

- **ML / LLM** для прогноза: нет данных для обучения, непрозрачно для жюри, сложнее защищать «честность»; ТЗ явно задаёт **детерминированные правила**.

- **Реальный скоринг API** — в разделе «не нужно» для прототипа и в «следующих шагах» после MVP.
